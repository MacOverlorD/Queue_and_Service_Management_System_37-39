## 1. Stack and changes from the reference

| Part | Choice |
|---|---|
| Client | React 18, TypeScript, Vite (built to static files) |
| API | Node.js 24, Express, TypeScript, Prisma 6 |
| Database | PostgreSQL 16 on Cloud SQL (PostgreSQL 17 for local development) |
| Image | One image from the root `Dockerfile`: the API serves the built client and the `/api` routes on the same origin |
| Tests | Vitest and Supertest (server), Playwright (e2e, run locally) |
| CI and release | GitHub Actions: `ci-docker.yml` and `deploy.yml` |
| Cloud | Cloud Run (service and migration job), Cloud SQL, Artifact Registry, Secret Manager |

Changes from the starter kit:
- One container serves UI and API, so there is no nginx and no separate client image.
- The seed refuses to run with `NODE_ENV=production` unless `SEED_PASSWORD` is set. The development default password is never used in the cloud.
- The kit's admin secret is stored as `qms-seed-password` and reaches the migration job as `SEED_PASSWORD`. The `--demo` option of `deploy.sh` is not used.
- The smoke test checks `/api/health` (database must be `up`) and `/`. The kit's optional token login check was removed because this API uses a session cookie.
- The client has no unit tests, so CI builds it instead of testing it.
- Cloud SQL storage auto-increase is off (`--no-storage-auto-increase`).

## 2. Environment variables

All configuration comes from environment variables. `.env.example` lists them with placeholders only.

| Variable | Purpose | Secret | Where the value comes from |
|---|---|---|---|
| `DATABASE_URL` | PostgreSQL connection used by Prisma and the API | Yes | Local: `.env` (placeholder in `.env.example`). Cloud: Secret Manager `qms-database-url`, generated by `deploy.sh`, never typed |
| `TEST_DATABASE_URL` | Separate database the tests reset on every run (its name must contain `test`) | No (throwaway) | `.env` locally, CI workflow value (`queue_test`) |
| `SEED_PASSWORD` | Password of the seeded accounts (stored as bcrypt hashes) | Yes | Local: `.env.example` placeholder. Cloud: Secret Manager `qms-seed-password`, generated, never printed. Required in production |
| `NODE_ENV` | `production` enables the Secure cookie and hides error details | No | Image and Cloud Run set `production`. Compose sets `development` so the cookie works over plain http on localhost |
| `PORT` | Port the API listens on | No | Cloud Run injects it. The image default is `3000` |
| `CLIENT_ORIGIN` | Browser origin allowed by CORS in development | No | `.env`. Not needed in the cloud (same origin) |
| `SESSION_TTL_HOURS` | Session lifetime (decision D-10) | No | `.env`, default 8 |
| `TZ` | Container time zone | No | `Asia/Bangkok`, set by `deploy.sh` |

## 3. Build, test, run, migrate, seed

Prerequisites: Node.js 20 or newer, Docker with Compose, and for tests a local PostgreSQL.

Run everything from a clean clone with Docker (check C-03):

```bash
git clone https://github.com/MacOverlorD/Queue_and_Service_Management_System_37-39.git
cd Queue_and_Service_Management_System_37-39
cp .env.example .env
docker compose up --build -d
curl http://localhost:3000/api/health        # {"status":"ok","db":"up"}
docker compose down                           # data stays in the volume
docker compose down -v                        # also deletes the data
```

Compose starts `db` (PostgreSQL), `migrate` (runs `prisma migrate deploy` and the seed, then exits) and `app` (the image Cloud Run runs). Open http://localhost:3000 in the browser.

Without Docker:

```bash
cp .env.example server/.env
npm run install:all
cd server && npx prisma migrate deploy && npm run prisma:seed
npm test                                      # server tests, needs the test database
cd ../client && npm run build
```

The seed is rerunnable: users, queues and assignments are upserted and sample entries are created only for queues that have none.

## 4. Continuous integration

`.github/workflows/ci-docker.yml`, workflow "CI & Docker Build", job `test-and-docker`.
- Runs on every pull request into `main` or `sprint1-staging`, by hand, and as a reusable workflow called by `deploy.yml`.
- Steps: syntax check and offline tests of the deploy scripts, server tests on a PostgreSQL 16 service (`queue_test`, migrations applied by the test setup), client build, `docker build` of the root image.
- `permissions: contents: read`. The database credentials are throwaway values for the CI container.

Merge gate: the ruleset `protect-main` is Active on `main`, the bypass list is empty, a pull request with 1 approval is required, and the status check `test-and-docker` must pass on a branch that is up to date. Force pushes and deletions are blocked.

The first deployment was done once from Cloud Shell with `deploy/deploy.sh` (dry run first with `DRY_RUN=1`, read, then real). The script is idempotent. It creates the registry, Cloud SQL instance, database, runtime service account, secrets, migration job and service, and it generates the database password and the seed password with `openssl`. Later deployments are done only by the pipeline.

Data persists in Cloud SQL, not in the container, so it survives a redeploy and a database restart. Cookie sessions are stored in the database. ## 6. Release procedure

1. Create an Issue labelled `lab5` for the change.
2. Branch from `sprint1-staging`, name it with the Issue number (for example `lab5/36-visible-change`). Write the failing test first when the change has behavior.
3. Open a pull request into `sprint1-staging` with `Closes #N`. CI runs `test-and-docker`. The other student reviews with a specific comment and approves. Authors never approve their own pull request.
4. Merge with a merge commit.
5. Before a release, merge `main` into `sprint1-staging` if staging is behind (the ruleset needs an up-to-date branch).
6. Open the release pull request `sprint1-staging` into `main`. CI runs again. The other student reviews and approves, and the owner merges with a merge commit.
7. The merge to `main` starts the workflow "Deploy demo": CI again, then login to Google Cloud through Workload Identity (no key), `docker build` and push of `qms:<full commit SHA>`, `deploy/release.sh` (verify the image, update and run the migration job, update the Cloud Run service by digest and send traffic to it), then the smoke test of the public URL.

Which commit is running: the run summary of "Deploy demo" lists the image tag (the full SHA of the merge commit on `main`) and the image digest. The same digest is shown by
`gcloud run services describe qms --region asia-southeast1 --format='value(status.latestReadyRevisionName,spec.template.spec.containers[0].image)'`
and in Artifact Registry, where the tag is the commit SHA.

Rollback (documented, not exercised in this lab): run the workflow "Deploy demo" by hand and enter the full 40-character SHA of an image that already exists in `image_tag`. Tests, build and migration are skipped, and the service is pointed back to that image.

If a deployment fails, read the failing step in the Actions log first (and the Cloud Run job log for a migration error). Fix it with a new Issue and pull request. Runs and commits are never deleted or rewritten.

## 7. Safety rules we followed

- The repository is public, so no secret is committed: no `.env` with real values, no connection strings, no key files, and no screenshot shows one.
- No service account key was created. The deploy account authenticates through Workload Identity Federation.
- An AI assistant helped draft code and documents. Every cloud command was read by a person before it ran, and no assistant changed billing, IAM or the database on its own.
- Cost control: budget alert, Cloud Run minimum 0 and maximum 3, smallest Cloud SQL tier, storage auto-increase off.
